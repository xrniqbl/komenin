# Refund reconciliation

Verified Midtrans refund, chargeback, and partial-refund notifications are persisted as `RefundReconciliation` receipts before an HTTP 200 response. Persistence or processing failures return 500 for gateway redelivery. The `eventKey` deduplicates replay; partial refunds require the gateway's `refund_key` or `refund_id` for unique event identity. A transaction ID alone is not a partial-refund identity: it may identify the original charge.

The processor locks the receipt and order, checks the signed original `gross_amount` against the order, and processes receipt state and local ledger effects in one transaction. Prior applied partial amounts count toward a cumulative cap. A full refund after partial refunds requires an explicit `refund_amount` equal to the remaining balance. Missing identity, unknown order, inconsistent amount, or non-paid order is acknowledged only after the receipt is marked `needs_review`. Applied and resolved receipts are never reprocessed. AI credit clawback excludes previous refund ledger entries from remaining recoverable credits.

The admin billing page lists pending/review-needed receipts. Superadmins can retry *local accounting* or resolve without adjusting entitlements; both actions require a reason and leave an audit entry. Neither action calls Midtrans or sends money. Do not resolve a receipt without independently verifying the gateway event, the order, and any required manual ledger adjustment. The existing admin order-refund action also only reconciles an already-completed external refund.

Operational prerequisites: deploy the accompanying `RefundReconciliation` migration and regenerate the Prisma client before accepting webhooks. Until then refund notifications will fail and require gateway retry. This implementation does not poll Midtrans to discover missing notifications; unsupported gateway payloads without a unique partial refund identifier require human review. No end-to-end database/gateway refund was performed against production.
